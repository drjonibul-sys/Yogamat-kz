## 1.14.1 — 2026-11-21
Тип: Z (исправление масштаба)
- Причина автоувеличения: iOS Safari/«На экран Домой» приближает страницу при фокусе в поле ввода со шрифтом меньше 16 px. В таблице «Визиты» поле примечания было 14 px; кроме того, масштаб ничем не был зафиксирован.
- Исправлено: (1) `viewport`: `initial-scale=1, minimum-scale=1, maximum-scale=1, user-scalable=no` — масштаб страниц и окон 100%, без автоувеличения и щипка; (2) шрифт всех полей ввода, списков и текстовых областей не менее 16 px (`input, select, textarea { font-size: 16px !important }`); (3) `touch-action: manipulation` — двойное касание не увеличивает; `text-size-adjust: 100%`.
- Побочный эффект (по запросу): масштабировать страницу щипком нельзя. Размеры шрифтов и элементов не менялись.
- Тест `e2e19.py`: проверяет meta viewport; на 390×800, 834×1112 и 1112×834 для 12 экранов — шрифт всех полей ≥16 px, нет горизонтального переполнения, масштаб 1; плюс окна с полями. Проверено в Chromium; поведение iOS на реальных iPhone/iPad не проверялось.

## 1.14.0 — 2026-11-21
Тип: Y (новая возможность)
- «Доход» → «Аренда»: ручная корректировка за любые периоды, в том числе прошлые. У каждого месяца кнопка «Изменить»: фактическая сумма за месяц, переключатель «Оплачено» и дата оплаты (не в будущем). В строке месяца теперь видна его сумма. Кнопка «Настройки аренды»: сумма по умолчанию и месяц/год начала учёта; более ранний месяц добавляет недостающие прошлые периоды (затем их можно исправить вручную), неоплаченные месяцы раньше начала удаляются, а при наличии оплаченных периодов раньше нового начала сохранение отклоняется.
- Модель: у периода аренды необязательное поле `amount`. Сумма фиксируется при оплате (кнопка «Оплатить») и при смене суммы по умолчанию, поэтому оплаченные месяцы не пересчитываются. Суммы периодов учитываются в «Выплачено всего», в расходах на аренду по месяцам (Доход), в отчёте по платежам (PDF/CSV) и в списке «Платежи». Старые данные без `amount` читаются как раньше (по сумме по умолчанию). Проверка при загрузке копии: некорректная сумма/дата периода отклоняет файл.
- Только администратор (`updateRentPeriod`, `updateRentSettings`; тренер получает отказ, экран и так закрыт).
- guide.js ред. 1.14.0 (FAQ: «Как исправить аренду за прошлые месяцы?»). Тесты: store.test.js (41), e2e18.py.

## 1.11.1 — 2026-11-18
Тип: Z (исправление правила по указанию пользователя)
- ПРАВИЛО ПРОПУСКОВ изменено: пропущенное занятие СГОРАЕТ (с абонемента не возвращается). Раньше (1.11.0) оно возвращалось. Нажатие на ячейку: пусто → ✓ (списывается) → ✕ (остаётся списанным). Колонка «Пропуски» — число сгоревших занятий действующего абонемента (перенесённые не считаются).
- ПЕРЕНОСЫ — только вручную: автоматического переноса или снятия нет. Нажатие на ✕ открывает окно «Пропуск занятия» (для одного клиента и одной даты): «Перенести на выбранную дату» (выбор даты + окно подтверждения), «Снять пропуск (вернуть занятие)» (с подтверждением), «Оставить — занятие сгорает». Нажатие на ✕ больше не снимает пропуск само.
- Перенос: сгоревшее занятие возвращается, на новую дату ставится посещение (запись), итого занятие списано один раз — на новую дату. Условия: дата позже даты пропуска, не позже окончания абонемента, на этот день у клиента нет отметки/пропуска. В ячейке пропуска значок ↪ (подсказка «Перенесено на …»). «Отменить перенос» удаляет запись на новую дату, занятие снова сгорает; то же происходит, если запись на новую дату отменить в журнале/карточке или массовой отменой будущих записей. Если клиент всё же пришёл в день пропуска — отметка посещения возвращает сгоревшее занятие (для перенесённого сначала нужно отменить перенос).
- Данные: у пропуска поля `subscriptionID`, `transferredTo`, `transferVisitID`. Пропуски 1.11.0 (без `subscriptionID`) считаются как раньше по сроку абонемента; их занятия ранее не списывались.
- Права: отмечать, переносить и снимать пропуски могут и администратор, и тренер (как отметка визитов). Если перенос нужно ограничить администратором — одна проверка в `transferAbsence`/`clearAbsence`.
- guide.js ред. 1.11.1. Тесты: store.test.js (39, обновлён), e2e15.py (сгорание, подтверждения, ↪, отмена переноса, снятие).

- Данные: новый массив `absences` в базе (входит в JSON-файл и резервные копии, проверяется при загрузке, чистится при удалении клиента; старые копии без пропусков загружаются как есть); у клиента поле `attendanceNote` (примечание для таблицы, отдельно от «Заметок» в карточке). Отметка посещения снимает пропуск за этот день.

## 1.8.2 — 2026-11-18
Тип: Z (оптимизация запуска)
Анализ: запуск замедляли четыре вещи.
- Логотип `icons/logo.png` весил 350 КБ и грузился на старте (фон и экран входа) → уменьшен до 384 px, 52 КБ (внешний вид тот же).
- Service worker брал каждый файл приложения (≈12) сначала из сети и только потом из кэша: на слабой связи запуск ждал сеть. Теперь оболочка отдаётся сразу из кэша (запуск без ожидания сети, в т.ч. офлайн). Новая версия приходит как раньше: кэш назван версией, обновление ставит новый service worker / кнопка «Обновить». `version.json` по-прежнему идёт мимо кэша.
- Вход по PIN: 2000 последовательных обращений к SHA-256 (на iPhone каждое — отдельный асинхронный вызов, вход мог занимать секунды) заменены одним вызовом PBKDF2 (100 000 итераций, встроенный в систему). Старые PIN и ответы на контрольный вопрос продолжают приниматься; PIN при первом успешном входе тихо переходит на новый формат записи `v2$…`. Контрольные ответы переходят при следующей смене вопроса.
- Фоновая докачка 400 иллюстраций справочника начинается не сразу, а через ≈6 с простоя после запуска — не конкурирует с запуском. Скрипты в index.html с `defer` (разбор страницы не блокируется).
- Замер (Chromium, сеть 200 КБ/с, процессор ×4 медленнее): первый запуск 3,9 → 2,3 с, вход по PIN 0,24 → 0,10 с; повторный запуск ≈0,3 с. Не проверено на реальном iPhone/iPad.
- Тест: store.test.js (38) — переход старой записи PIN на новый формат.
- Остаётся: первый запуск после установки ограничен скоростью сети (≈230 КБ скриптов/стилей, на GitHub Pages сжимаются); дальше возможна склейка скриптов в один файл.
